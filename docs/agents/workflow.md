# 工作规则

默认使用中文沟通和写文档，代码标识符沿用项目风格。

### 先想清楚再动手

- 先查仓库事实，再设计或编码。按 `docs/agents/domain.md` 阅读领域术语、相关 ADR 和方案；
  未知信息明确写为待确认项，不编造 API、路径、版本、错误码或性能数字。
- 写明会影响实现的假设。需求有多种会改变方案方向的理解时，列出选项请用户选择；
  其余细节采用最保守的可行方案，并在交付说明中写明假设。
- 有更简单的做法就提出；有证据支持的反驳或重大风险应直接说明，不为附和用户改变技术结论。

### 简单优先

- 写代码前使用 ponytail skill 分析复用性，只实现当前需求。复用顺序：
  项目现有实现 → Rust 标准库 → 已引入的依赖 → 最小必要实现。
- 按实际职责创建模块，不预建空模块，不增加未要求的功能、配置开关或扩展层；
  不为单一实现抽象 trait 或工厂，除非现有库接口要求。
- 一个函数或方法只做一件事，不超过 50 行；单个代码文件不超过 5000 行，超过就按职责拆分。
- 不为已由类型、构造流程或前置校验证明不可能发生的内部状态重复加兜底；
  外部输入、网络失败、超时、取消和资源释放属于真实边界，不得省略处理。
- 新增依赖前说明现有实现和标准库为何不足，并核实维护状态、Rust 工具链兼容性、
  Linux CPU 支持、许可证、体积和传递依赖；原生依赖还须确认 ABI 与部署要求。
- 模块契约集中在对应 Rust 模块的 `//!` 文档，公开 API 的约束使用 `///`；
  其余注释只保留必要的安全依据、兼容性来源、非显然约束和有明确上限的 `ponytail:` 简化说明，
  不用注释复述代码，不为了集中注释创建空模块。

### 外科式改动

- 每一处 diff 必须对应本次需求、根因修复或必要的验证与文档同步，沿用所在文件的命名、结构和风格。
  不顺手重排格式、改名或重构相邻代码。
- 修 bug 前追踪完整调用链和所有调用方，在共同根因处修复，并验证受影响的其他路径。
- 同批删除本次改动造成的无用 import、变量、函数和文件；既有无关问题只写进交付说明。
- 保留用户已有的未提交改动；提交时只纳入本任务的变更，不覆盖、回退或清理其他工作。

### 目标驱动

- 动手前给出可验证的完成标准。修 bug 先写失败的复现测试，加校验先写非法输入测试，
  重构前后使用同一组测试验证行为。
- 多步任务先列计划，每步写成“步骤 → 验证：检查什么”。完成以实际执行的验证为准；
  未执行的检查不得报成通过，不删测试、不改断言绕过失败。
- 变更行为时同步测试和权威文档。协议、输入限制、推理并发、排队和退出处理需覆盖相关的
  失败、超时、取消与重复请求路径；引入重试时验证其语义和资源开销。
- Cargo 工程建立后，按改动执行 `cargo fmt --check`、`cargo clippy --all-targets -- -D warnings`
  和相关 `cargo test`；Shell 调用遵循根目录 `AGENTS.md` 引用的 RTK 约定。仅改文档时检查内容、引用和 diff，
  不把尚不存在的构建或测试报告为通过。
- 模型兼容性必须使用固定参考样例和真实模型验证，明确比较容差；缺少权重或运行环境时，
  说明未执行的验收项，模拟测试和静态检查不能替代真实推理对照。
